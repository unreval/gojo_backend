## 1. 问题、事实与设计边界

目标是让用户更细致地理解角色当下的感情、靠近与退缩的原因，避免不同阶段都得到“挚友”式答复，并减少固定提示和生成链路造成的重复表达。

### 1.1 用户提供的线上事实

以下来自用户只读查询，本轮没有重新查询生产，也没有确认生产 build 与本地 HEAD 一致。

|---|---|---|---|
| gojo | warmth / intimacy / trust / attachment 均为 100；commitment 75；passion 33；pending_passion 0 | 总和约 73，其中 boundary_violation 69.3 | 深厚的挚友 / 亲情 |
| geto | warmth 4.8；intimacy 100；trust 54；attachment 6.03 | boundary_violation 61.2 | 疏远 / 厌恶 |

gojo 的 `last_updated` 为 2026-10-01 05:31 UTC，即 2026-10-01 13:31（Asia/Singapore）。该字段表示账本更新时间，不能当作最近互动时间。

这些值不能证明 gojo 已爱上用户、geto 厌恶用户，或用户确实多次越界。封顶值丢失了继续上升的幅度；摩擦总数也缺少本轮可验证的逐事件来源。不能据此补写角色感情、用户事实或关系身份。

## 2. 饱和修复：长期账本、近期窗口与趋势

### 2.1 保留账本，重新定义展示

`rel_state` 保持现状，不把四个 100 降为新起点，不扩大最大值，不用新的分数反向校正它。原有 provenance 继续保留。`value_after-value_before=0` 的封顶日志不能恢复当时本想增加多少，因而不能把旧账本增量当作新窗口的完整输入。

用户面板默认展示“近期靠近／退缩／拉扯／暂无足够观察”、证据更新时间和原因摘要。长期数值只在明确打开的调试视图中显示为“历史累计指标，部分已封顶”；卡片不包含数值、旧标签或关系身份标签。geto 不能因旧负面标签默认被写成厌恶用户。

### 2.2 存储与更新

拟扩展 `rel_interaction_stats`：增加 `subjective_annotation` JSONB、`policy_version`、`source_snapshot_hash`、`occurred_at`、`processed_at`；注解包含固定标签、置信度、引用范围、接收或拒绝原因。原有 direction、source_event_id 等继续使用。新增有条件唯一约束 `(user_id, character_id, source_event_id, policy_version)`，先审计旧重复行；旧行没有 v2 注解时不自动纳入。

注解是模型候选和程序验收记录，不能独立证明事件。真正输入始终是 active canonical 用户事件，身份使用结构化 ID，用户消息跨文本、图片说明和语音转写按 event_id 去重。故事台词、日记、主动生成文本和离线内心文本都不增加近期关系样本。

近期窗口取最近 7×24 小时；对照窗口取此前 7×24 小时；分析最多扫描 14 天。以窗口结束时刻T为锚，向前切分恰好7个24小时的半开区间，时间计算统一用UTC，展示转为用户时区。另按UTC自然日做采样限额：每类标签每天最多接收3个独立用户事件，间隔至少60分钟，同一语义类的同轮重复表达只计一次，避免刷屏抬高趋势。

canonical 用户事件落账后异步排队；合格批次提交后重算；来源删除、纠正、撤回时立即使相关投影失效并重算；读卡片时按当前时钟计算衰减。无新事件时无需调用模型或定时写账本。缓存只存于现有 reader 缓存，按用户、角色、事件 watermark、来源有效性版本、规则版本、时间桶区分，TTL 60 秒；失效检查优先于 TTL。缓存丢失只增加重算，不改变状态。

### 2.3 计算契约

先由第3节的规则为事件生成三个观察分量 `z_e`：亲近互动、收缩互动、互动压力，各在 `[0,1]`。合并本轮标签的基础贡献为a_e/v_e，亲近取 `clip(max(0,a_e)/0.12,0,1)`，收缩取 `clip(max(0,v_e)/0.12,0,1)`；压力在DISAGREEMENT时为0.6、仅REQUEST_SPACE时为0.3、其余为0，不把调情或直接提问当作施压。修复的负贡献用于内心V变化，近期收缩分量不记为负。AMBIGUOUS不进入样本，已确认不相关的OTHER为零观察。它们描述角色对本次互动的主观读法，不是用户心理或trust / intimacy的替代量。

对每个 24 小时桶，合格事件使用 `q_e=confidence` 加权：`b_d = Σ(q_e×z_e) / max(1, Σq_e)`；空桶为 0。对任意窗口结束时刻 `T`，桶权重为 `w_d=2^(-age_d/3天)`，取桶中心相对 T 的年龄；窗口分量 `R(T)=Σ(w_d×b_d)/Σw_d`。分母包含全部七个时间桶，确保单个旧事件不会因分子、分母同时衰减而永远保持强度。

近期为 `R(t)`，对照为 `R(t-7天)`，各自按各自窗口结束时刻算权重。方向差 `D=(R_亲近-R_收缩)_近期-(R_亲近-R_收缩)_对照`：`D≥0.12` 为更靠近，`D≤-0.12` 为更收缩，其余为变化不明显；近期亲近与收缩均≥0.25 时附加“有拉扯”，不互相抵消。

每个窗口至少 3 个合格事件、覆盖至少 2 个日期，才显示对比趋势；不足则显示“观察不足／正在形成”，不把 0 当作疏远。来源覆盖率、抽样截断和最新 processed_at 一并可见。14 天外不参与窗口；主观冲动另按第 3 节衰减。沉默不会降低账本 trust，也不证明用户拒绝。

验收例：同样四项 100 的两条合成历史，一条近期持续关心、一条近期要求空间，必须给出不同窗口描述；事件失效、缓存清空与重复处理后，结果必须与从有效原始事件重算一致。

## 3. 内心状态生产者：受限传感器与确定性投影

### 3.1 固定标签与置信度

LLM 只标注“消息里出现了什么表达”，只看用户事件和最少必要上下文；不看长期数值、旧身份标签，不输出感情结论、用户动机、自由原因、数值增量或新 topic_id。最多每事件 3 个标签。

| 标签 | 可观察内容 | 靠近 A / 回避 V 基础贡献 | 原因代码 |
|---|---|---|---|
| CARE_OFFER | 问候、关心、提供支持 | +0.08 / 0 | care_received |
| PERSONAL_DISCLOSURE | 用户主动分享自己的经历或感受 | +0.06 / 0 | openness_received |
| AFFECTION_OR_FLIRT | 当下明确亲昵、调情表达 | +0.10 / 0；与有效边界冲突时V才+0.03 | affectionate_signal |
| REQUEST_CLOSENESS | 希望多相处、靠近 | +0.06 / 0 | closeness_invitation |
| REQUEST_SPACE | 要求暂停、少联系或保持距离 | 0 / +0.12 | requested_space |
| DISAGREEMENT | 针对当前互动表达不满或分歧 | 0 / +0.06 | unresolved_disagreement |
| REPAIR_OFFER | 道歉或提出修复当前分歧 | +0.06 / -0.04 | repair_received |
| BOUNDARY_ACK | 明确承认并尊重已知边界 | +0.05 / -0.03 | boundary_respected |
| FEELINGS_QUESTION | 直接询问角色感情 | 0 / 0 | answer_requested |
| DECLARATION_CANDIDATE | 明确表态、确认或撤回的原文候选 | 0 / 0 | explicit_statement_pending |
| AMBIGUOUS / OTHER | 反讽、引用、无法确定／不相关 | 0 / 0 | insufficient_observation |

每项输出限定：event_id、标签枚举、`confidence∈[0,1]`、原文字符范围和 hash、`target_ref`、literal / quoted / hypothetical / ambiguous 的 mode。event_id 和 target_ref 必须来自程序给出的枚举，不能由显示称呼推断。引用范围必须与 canonical 原文完全匹配；需上下文才能判定时列全 dependency_event_refs。

置信度≥0.85、mode=literal、主体和来源校验通过才进入主观增量；0.65–0.85 为待观察，不改内心；低于 0.65、标签冲突或反讽不确定则 unknown，不强行挑一个标签。模型自报置信度不是已校准概率；上线前必须在标注集校准，未达精度门槛就抬阈值或关闭该标签。批次逐条验收，一条错误不牵连其他合法事件。

FEELINGS_QUESTION 和 DECLARATION_CANDIDATE 只提出候选。里程碑、用户边界事实和应答义务仍要确定性确认。诸如“你讨厌我吧”“假如我们交往”“故事里他说我爱你”不能变成声明。调情不会天然制造回避或纠结；表中条件增量由规则读取有效边界的scope与引用决定，传感器不能自己宣布“角色害怕亲密”。

### 3.2 主观投影的唯一存储与原因目录

复用 `cognitive_hypotheses`，以 `relationship.internal_conflict` 作为本方案主观快照的唯一当前记录，metadata 存 A、V、纠结 C、原因、窗口摘要、规则版本和完整来源。`engagement_style` 与 `romantic_openness` 由同一快照只读投影为互动方式与亲昵表达开放程度，不另存另一套分数；既有合法 canonical 项须保留类型与来源，不能被主观候选覆盖。

快照保持主观类型，不能自动 promote 到 `cognitive_beliefs`。需扩展现有 reader 的类型判断；不能仅添加 schema 键就声称已有生产者。`romantic_label` 完全独立，只由第 4 节里程碑链生产。

`cognitive_cycles.hypothesis_updates / evidence_refs / cycle_summary` 记录输入快照、接收拒绝决定、增量前后、限幅、时间和版本；正式事务由现有 deterministic revision 提交。新增逻辑职责是主观投影校验，不建立新的关系裁决服务，不复活旧 observer writer。

原因目录除表中代码外，仅允许：`active_boundary_tension`（靠近冲动与有效边界冲突）、`unanswered_feelings`（欠答案）、`canon_expression_limit`（版本化角色表达约束）、`insufficient_observation`。最多显示 3 个原因，按贡献排序。active_boundary_tension 必须同时引用靠近事件和有效边界；角色设定原因另列 config_ref 与版本，不能把配置冒充用户事件。

每个原因保存 trigger_event_refs、dependency_event_refs、quote_range、contribution、first_seen、last_seen、expires_at、snapshot_hash。不得自由编造“害怕再次失去”“用户不值得信任”等未支持理由。用户原话被删除或纠正后，相关原因立即移除，不能仅靠旧日志继续有效。

### 3.3 动力、滞后、限幅与回放

A、V、C 在 `[0,1]`；A 与 V 可同时高。没有合格来源时为 unknown，不用长期 100 当基线，不补猜历史内心。初次合格事件从 0 起建立投影，同时标记 warming_up。

对独立事件，按表贡献乘confidence；本轮合并后每个动力 `|Δ|≤0.12`。每事件只消费一次，按首次accepted_at划分的固定UTC 5分钟逻辑桶，每个动力合并影响≤0.18，与Provider传输批次无关。每UTC接收日、每角色、每个动力的正向总量和负向总量分别≤0.30，独立记账，防止靠正负抵消绕过上限；并发worker通过同一事务和版本比较扣额度。额度计实际应用的绝对增量，衰减另记，不重复消费。重试、渠道切换与重新分批不获得新额度。

合格证据进入后的有界目标是上一衰减状态加接收贡献；投影朝目标推进，每次最多移动目标距离的0.35，并受上述上限约束。目标先clip到[0,1]，超出容量的贡献丢弃并留痕，不积成以后自动释放的隐藏动力。批次仅决定传输；给定相同接收时间，重算按 `(accepted_at,occurred_at,event_id)` 逐事件应用固定顺序，分批大小不能改变结果。趋势用occurred_at，内心演化与每日额度用首次accepted_at；迟到标签只能成为现在新接收的观察，不能补写当时已知的感情。A/V无新证据按半衰期7天衰减；连续空白只让推断变弱，不写拒绝或惩罚。

纠结目标 `C*=min(A,V)`，前提是靠近与回避两侧都有有效支持，或有效边界与靠近事件构成冲突；否则C为未观察到。同一事件可以有两个不同有效表达片段，但同一句话不能仅凭换标签制造冲突。边界存在本身不抬高V或C；必须有本轮合格事件与该边界scope匹配，才按表中的条件增量处理。C采用同样0.35平滑、单事件最大变化0.08、每日双向上限各0.20；无新证据半衰期3天。进入“明显纠结”需C≥0.30且连续两次独立事件支持、间隔≥30分钟；退出需C≤0.18。A/V强度档进入门槛0.20 / 0.45 / 0.70，退出分别低0.07，避免句句翻转。

限幅约束正常新增推断；来源撤回必须立即重建，不能用滞后维持失效来源。明确拒绝、撤回和联系限制先在 canonical 表达授权中即时生效，主观 A 尚高也不能越界表达。

严格区分两种回放：同规则、同注解、同接收时间和额度决定得到相同历史结果；规则升级或来源失效则从合法源生成新版本并比较差异。保存 processed_at / accepted_at，避免把今天回填的标签伪装成当时已知。不得重新调用 LLM 来声称“确定性回放”；重标注属于新模型版本的重新估计。

### 3.4 调用预算、批量与失败

建议异步传感器每 5 分钟或累计 8 条合格事件触发，每批最多 8 条、总输入≤2400 tokens、输出≤800 tokens；只读 canonical 用户文本，过长消息按有记录的截断策略标为 partial，不能声称覆盖整轮。没有新增事件不调用。

初始预算：每用户／角色每天≤6次实际 Provider 尝试、≤18,000输入和≤6,000输出 tokens；每用户跨角色合计≤12次、≤48,000总 tokens。传感器单批不即时重试，失败消耗实际额度；认证失败熔断，临时失败退避，剩余事件允许之后重新入队，必须标出迟到时间和旧状态。

共用现有 spend guard，并为未来与 `HUMAN_MEMORY_DESIGN.md` 的后台任务共享额度预留统一入口；现有事实 Slow Loop 继续 `model_calls=0`。传感器关闭、失败、超额或超时：这一轮不更新主观状态，保留可验证旧投影并标记 stale；没有旧投影则 unknown。不能用缓存生成文本、日记或规则猜标签补数。聊天生成不等待传感器，当轮直接提问由确定性问题识别处理。预算和计费上限均为产品待定值。

## 4. 里程碑与“欠答案”

### 4.1 里程碑只认明确证据

沿用用户指定的“明确表态、双方确认、撤回”原则，具体要求如下。

| 事件 | 必需证据 | 可产生的结果 |
|---|---|---|
| 单方表达感受 | 有主体、对象、时间范围的直接原话 | 记录某方确实表态；不证明双方身份 |
| 提议定义关系 | 明确 proposition、提议方、对象、scope 与源事件 | 未决提议，不自动确认 |
| 双方确认 | 同一 proposition 的角色明确表态与用户明确接受，双方事件均 active，reply_to 或程序可确认的上下文绑定 | 正式 revision 更新对应里程碑和窄语义 |
| 明确拒绝或撤回 | 同主体对明确提议／表态的直接拒绝、撤回，引用目标或绑定 scope | 当前许可立即收缩，保留历史时间线 |
| 删除或证据失效 | canonical source 状态改变 | 依赖结论失效、重新裁决；不伪造新的拒绝事件 |

角色生成文本只能证明“角色说过这句话”。若要成为表态，必须先过生成闸门、成功 commit 为 canonical assistant event，并经既有 evidence/adjudication 校验；结构化声明 intent 是候选，不能直接写 stance。用户是否接受仍要独立用户证据，不能拿角色自己写的“你也答应了”当确认。

首期采用窄确定性语法与显式提议引用，未知自然语言保持 pending，允许清楚询问确认，不强迫用户输入固定暗号。`AFFECTION_OR_FLIRT`、A/V/C、高 attachment、承诺或次数不能确认身份。“我喜欢你”要区分单方心情与双方关系定义；`romantic_label` 的 affirmed / declined / other 必须带明确 proposition 和 scope，不能以单方感受代替双方确认，也不能把拒绝一次行为永久泛化成拒绝所有亲密表达。

复用 Cognitive question 的 current_judgment / resolution 与 `rel_declared_stance`，不新增 milestone authority 表。当前 question 协议对 resolved 记录不支持通用 reopen；后续撤回须通过正式 revision 的失效／新版本契约，或新建引用旧命题的版本问题，不能强写状态绕过 `question_transition_status`。来源失效时 reader 必须先停止授权，即使后台尚未完成重算。

### 4.2 直接提问识别

在 canonical 用户事件落账后，以确定性的有限语法检测中文、日文和英文的“第二人称对象＋感情谓词＋询问”：如“你喜欢我吗”“你对我是什么感觉”“你为什么总躲着不答”“私のこと好き？”“Do you have feelings for me?”。同时覆盖明确索取答复的祈使句。

排除整段引用、故事主题、第三方转述、假设句、否定请求“别回答这个”、无明确接收角色的群聊和不指向当前角色的“你”。用当前 source、reply_to、对象和上下文依赖约束消歧，不用单独关键词“喜欢”判定。不能识别的表达由传感器提候选，确定性校验仍无法确认时只列“可能需要正面回应”，不增加强制欠账。

首期允许漏掉复杂反讽，不允许把故事对白记成用户逼问。消息首次排队时即可登记待答；角色忙碌、延迟回复或生成失败不算回避。

### 4.3 存储、回避与清偿

每个提问 episode 复用 `cognitive_questions`，稳定键由用户、角色、ask_event_id、scope 生成；重复问同一问题时关联当前未结 episode。metadata 增加 `answer_debt`：ask_event_refs、last_ask_at、eligible_reply_count、evasion_count、last_attempt_ref、force_due、answer_mode、settled_by、policy_version。应答事实的唯一来源是已提交 assistant event 和现有 generation receipt，不另建 debt 表。

“回答感情问题”与“确认关系命题”使用不同 question scope。服务应答 question 的 resolved 只表示本次问题得到正面处理；不写 romantic_label，不等于双方确认。

生成候选可附带 `answer_intent`：question_ref、kind（present_feeling / uncertainty / explicit_boundary / deferred）、quote_range、source_snapshot_ref。这是应答候选元数据，闸门必须检查真实 JP/ZH 文本，而非相信模型自报 answered。

正面处理至少包含：回应当前感情问题、给出现有来源允许的当下感受或明确不确定／限制、解释一个有支持的原因。内心未知时可坦率说无法确定，并说明还缺少什么；不能捏造心动凑答案。只说“你猜”“别想太多”“先讲个笑话”“我们一直是挚友”，或只调情而不回答，视为回避。仅 emoji 或省略号在普通聊天仍合法；在强制应答轮不能清偿欠账。

受支持的明确拒绝、说明不能回答及其具体限制可以清偿本次服务应答；“以后再说”只记 deferred，不清偿，也不自动创建承诺。清偿先过闸门，再由正式问题 writer 引用已 commit 的回答事件记录。被拒绝的候选不算角色实际回避，另计 gate_rejection；同一 receipt 的重试或回放不重复计数。

若清偿来源失效，reader 立即恢复待处理提示；由于旧 resolved question 不能直接 reopen，创建引用同一 ask 的修订 episode，旧记录保留审计且不继续当有效清偿。用户明确撤回提问时归档义务，不能当作已回答。

### 4.4 阈值与强制回应

- 第一次直接询问：本轮卡片已要求正面处理；允许一次有理由的延后，记录未答。
- 两次实际提交的回避、用户第二次直接追问，或提问后超过 24 小时且已有至少一次可答复机会：`force_due=true`。单纯离线 24 小时不触发主动补答。
- 强制轮：第一段用 1–3 句先回应，之后才允许玩笑、故事或调情；不得用身份标签替代回答。支持何种感受就答何种，证据不足允许明确“不确定”。
- 每条用户发起的可答复消息最多处理一项，优先本轮问题、再最早欠项。用户说不想继续、已有联系限制或发生紧急主题时暂停插入；暂停与原因留痕，不永久清偿。
- proactive 只有用户允许且当前触发与问题相关时才补答，不新增催问式主动消息；delayed 按原始提问 scope 补答。故事模式最多在故事前加短应答，不把主角台词充作答复。

默认用户面板不展示“欠账次数”，只提供可选“这个问题还没正面回答”提示。该机制承担角色的答复义务，不能指责用户追问或要求用户继续互动。

## 5. 内心卡片 v2 与表达范围

卡片由现有 relationship reader 组合合法主观快照、当前有效边界、里程碑和待答 question；先检验所有依赖，再渲染。它不显示原始数值、不显示旧关系标签、不输出 romantic_label 枚举，也不自行选择身份。

以下为模板；方括号由程序填充，不由生成 LLM 即兴补写。示例不代表 gojo 或 geto 的真实内心。

```text
【当下内心｜v2】
观察：截至[本地时间]；[已观察／观察不足／更新滞后]。
近期：[更愿意靠近／更倾向收缩／有拉扯／变化不明显／观察不足]。
靠近：[轻微／持续／明显／尚不清楚]；因为[允许原因短句]。[来源引用]
回避：[轻微／持续／明显／尚不清楚]；因为[允许原因短句]。[来源引用]
纠结：[未观察到／正在形成／明显／尚不清楚]；[两侧冲突的具体原因]。[来源引用]
待回应：[无／问题原文的必要片段]；[本轮先回答／可以说明延后原因]。
里程碑与表态：[何时提出／单方已表达／双方明确确认过该命题／已撤回／尚无明确证据]。[有效引用]
表达范围：可说[当前有支持的主观感受与原因]；必须遵守[有效边界]。
本轮路线：[允许路线之一]；避免重复[最近句式的短摘要]。
```

缺字段时省略对应原因，不渲染“纠结很深”之类默认文案。里程碑只描述证据状态和行为，例如“双方明确回应过交往提议”，不放“恋人／挚友”等身份标签。原始声明全文留在可展开的来源详情，生成授权单独读取结构化命题，不靠卡片自然语言裁决。

表达区间建议：靠近低时可好奇、关心；中等可表达愿意相处或期待；明显且没有对应边界时可说“我会期待你的消息”“刚才有点心动”等有支持的主观体验。回避可以说需要空间、暂缓或顾虑；两侧都有支持时可坦率表达“想靠近，也有顾虑”。这些是允许的语义范围，不是逐字固定台词。

“未确认身份”不能被写成“只能永远做朋友”；“有主观心动”也不能写成“我们已经交往”。角色设定须拆为人格风格和明确的表达禁限，并版本化列出实际约束；是否允许关系发展是产品选项，不能在模板里偷偷预设永久挚友。

卡片建议控制在 500 中文字／约 700 tokens 内；详情只保留来源引用而非大量原文。生成只看到本轮必要字段；数字、legacy_label 和调试面板移出 Prompt，降低量表与身份词诱导。具体 token 上限以真实 tokenizer 测量为准。

## 6. 旧“雷区”机制：停用、审计与兼容

### 6.1 来源与风险

旧 `relationship_signals` 让 LLM 输出自由 `topic_hint`、severity、intentional 与 high / medium / low。`relationship_boundary.handle_boundary_hit` 用这些输入计算摩擦，再调用 `apply_friction / apply_trust`。尽管配置写着 low 的倍率为 0，该 helper 没有使用此置信度倍率，底层 writer 也只是记录 confidence；直接调用时 low 仍可能增加摩擦或扣 trust。

`rel_boundary_hits.known_by_user` 是累计布尔值，不能单独证明用户收到并理解某条边界；`mark_boundary_known` 可能创建 `source_event_ref=boundary/<topic>`，不是有效 canonical event ID，当前 stance reader gate 应拒绝这种无原始事件绑定的行。自由 topic_hint 还会造成同一话题拆分、不同话题合并，普通追问被算成恶意，以及“先推断用户明知，再加倍惩罚”的循环。

上述是静态风险，不证明线上 69.3 或 61.2 全部错误，也不证明当前部署仍在调用。当前主路径已移除 observer，本设计不恢复它。friction 较高不进入主观 V，不作为关系身份依据。

### 6.2 建议方案

1. 默认继续停用旧 observer 到 boundary writer 的路由；另审计实际调用者和部署版本。设独立 kill switch 禁止旧 boundary helper 被隐式调用，不关闭合法明确边界的表达限制。
2. 显式边界使用稳定 boundary_ref，来自用户明确拒绝、角色有效表态或版本化设定；topic_hint 仅是候选，不能成为身份键或事实。普通询问感情不默认违规。
3. “已告知”需有效表态事件、明确对象和时间先后；是否理解、是否故意不能只由阅读回执或 LLM 推断。缺明确信息则 unknown；不使用恶意倍率。
4. 首期真实明确越界仅产生当轮表达边界及有界主观回避原因，不给 `rel_state` 新增摩擦。将来若恢复数值影响，必须独立评审 deterministic policy、有效来源、low=0、每日上限、去重和原子 provenance，不能顺便恢复旧代码。

### 6.3 不改历史行的审计与迁移

未来经授权只读导出 `rel_provenance_log`、原始事件、有效 stance 和相关部署信息，逐条归为 source_verified / ambiguous / missing_source / invalid_source。校验主体、事件时间、quote、policy_version、confidence 和当时有效边界。只凭 note、累计布尔值或旧 topic_hint 无法验证的行保持未核实，不能直接删除。

历史 `rel_state`、provenance、boundary_hits 行原样保留。新面板默认不让未核实 boundary_violation 影响趋势、内心和身份；调试页仍显示原历史值与审计提示。既有的、可验证的当前边界照常生效，不能因停用旧摩擦就放开限制。

选择重算时，仅从具备完整 canonical 来源的事件重算 v2 窗口与主观投影，写新 policy_version 的非权威注解和 Cognitive revision，不对 `rel_state` 执行 UPDATE。不计算“把 69.3 从 100 中扣回去”的补偿值：封顶、旧加权和缺失来源让这种反算不可识别。无合法来源的历史保持 unavailable，新观察从 rollout 时开始。

迁移采用 additive 字段／索引、shadow 读、版本指针切换，不 DROP、不覆盖旧日志、不自动生产回填。每批记录事件 watermark、源摘要、接受拒绝理由与前后结果。回滚只关新 reader / writer 并恢复旧的安全 panel；新注解保留为不参与读取的审计记录。若旧 generation Prompt 曾含标签，回滚也保持标签不作为身份授权，不能恢复已确认有风险的模型判分。

## 7. 统一生成后闸门

### 7.1 顺序与检查范围

统一契约是：构建版本化内心卡片与结构化授权 → 生成候选 → 协议解析 → 完整消息关系闸门 → 最终文本再次校验 → canonical commit / receipt → 已许可的交付与副作用。

闸门默认确定性、零 LLM 调用，检查完整 visible 消息及 JP/ZH 两侧，覆盖：

- 来源有效性与卡片版本是否过期；明确拒绝、撤回、边界是否仍生效。
- 未经许可的关系身份、双方确认、用户心理或过往事实断言；主观表达是否在允许范围。
- 应答义务：强制轮是否先正面回应、是否只是玩笑或旧身份措辞。
- 相邻段落是否矛盾，翻译是否增加一侧没有的关系承诺或身份声明。
- 最近句式重复与本轮路线是否冲突；重复属于软质量问题，不因此强迫生成新感情。

使用明确的声明／应答 intent、有限语义模板、否定／引用识别和中日英词表。intent 必须与可见片段相符；对高风险身份声明采用受限表达骨架，无法确定是否获得授权则拒绝该声明。自由自然语言的全部蕴含无法靠关键词证明正确，须在盲评中测漏检；不能宣称规则闸门理解了所有隐喻。

来源在生成期间变化时必须刷新授权再检验，失效声明不能凭旧 snapshot commit。最终 sanitizer、翻译或切段若改变文本，必须再次检查。候选被拒绝时不写表态、不清偿欠账、不执行 transaction、schedule、promise、offline_state 等副作用。既有协议、来源、日程和业务闸门继续保留。

### 7.2 各入口接入点

| 渠道 | 当前入口／路径 | 拟接入位置与特殊要求 |
|---|---|---|
| text | `route_chat.chat_text`，`/chat/text`，`_generate_or_none` / `_finalize_committed` | 组合现有 reject_fn；最终整理后再检查；位于 schedule intent、generation effects、assistant commit 和返回之前 |
| story | `route_chat` 的 `/chat/story`、`/chat/voice_story`；`route_story.story_generate` 的 `/story/generate` | 检查完整故事和对用户说的框架句；虚构人物台词不得升级为当前关系事实；独立 story 路径补最小用户身份／授权上下文，返回与 `/story/tts` 前验证来源或已验收文本摘要 |
| proactive | `/chat/proactive`、`/chat/voice/proactive`、`proactive_scheduler.generate_from_promise`；其他日程分享／日记反应 producer | 在消息入库、promise fulfilled、push 和 TTS 前检查；逐 producer 清点，不能只包 HTTP 路由；主动生成不反哺关系证据 |
| delayed | `delayed_reply.generate_delayed_chat_reply`，现有 route_chat helpers | 复用同一完整闸门；引用 pending 用户事件；通过并 commit 后才 resolve phone occurrence／pending inbox，重试不重复补答 |
| image | `route_image.chat_image`，`/chat/image` | 放在协议与 schedule 检查后、offline_state 与 commit_and_run_effects 前；图片 caption 属用户原始输入，视觉摘要／OCR 猜测不用于感情里程碑；新增文字推断不会扩大媒体事实 authority |
| voice_stream | `route_voice_stream.chat_voice_stream`，`/chat/voice_stream` | Provider token 只进入服务端完整缓冲；完整 JP/ZH 消息验收后才允许 text_jp、TTS、audio、assistant commit 与交付 |

`/chat/voice_text` 同样复用 text 闸门。实现阶段须扫描所有直接 Provider 调用和后台可见消息 producer，用渠道 contract test 证明覆盖；不以表格列了入口代替实际接入。

### 7.3 voice_stream 完整缓冲

必须缓冲整条逻辑 assistant 消息的所有段落，不是每句各自验收。闸门前禁止发送任何候选字幕、音频、预合成 TTS 或可见文本；可以发送不含内容的 thinking／heartbeat。首期建议最多 8 段、2000字符、生成时限20秒，超时或截断视为不完整候选，不能释放已经收到的半句。

通过后先获得稳定的 assistant_turn_id 与交付 receipt，再按通过的片段合成并发出 NDJSON；只对可验证的最终文本清偿应答，并记录完整 commit 与实际交付情况。commit 成功但断线属于交付未知，不重新生成或二次清偿，可用 receipt 恢复原消息；未交付时卡片可提示待送达。TTS 失败不撤销已提交文字，允许仅字幕交付，与现有音频可用性原则一致。

该调整会增加首段音频等待时间，改变流式交付时序，需要客户端合同测试。降低延迟只能优化完整生成和已验收 TTS 并行度，不能放行未经完整检查的首段。

### 7.4 一次重试、降级与额度

所有协议、翻译、日程和关系语义错误共用最多两个候选，即首次加一次修复，不能层层各重试一次。修复只给出失败代码和允许范围，沿用同一来源、卡片、种子、receipt；不改变 canonical 用户事件。独立 `/story/generate` 的五次循环也须在后续实现中并入这个总上限。

第二次仍失败或无修复额度时，确定性生成来源允许的最小双语回应：直接提问给出当下可支持的感受／明确未知及一个支持原因；其他聊天可给简短中性回应。模板按相同种子选可用变体，仍过全部硬闸门，不带任何业务 intent。来源未知时只承认未知，不能补编原因；无法安全回应则返回明确 generation_failed。

proactive 的失败默认取消本次可选消息，不硬发模板；delayed 只有通过的回应才能 consume pending；story 可返回通过验收的短故事或明确失败，不拿最后一条被拒绝候选作“最佳结果”。兜底清偿仅在真的正面回应且成功 commit 时发生，失败／取消不增加实际回避。

确定性闸门不增加模型调用；修复最多增加一次原生成模型调用，并计入现有实际 Provider 计数及共享额度。建议每用户每天新闸门引发的修复≤5次，超额直接降级；短窗口质量异常进入熔断。SDK 内部传输重试也计实际调用，需有总尝试上限，不能在两候选外形成隐形倍增。严格关系合规失败不可因预算不足放行；单纯重复措辞不单独触发付费修复。

## 8. 抗刻板与中转对照

### 8.1 按种子选择允许路线

先由 reader、明确边界、场景和欠答案筛出路线：直接说明、简短承认、解释顾虑、轻微玩笑后回应、具体关心、提出澄清、坦率保留不确定。强制答复时排除“仅玩笑”与“转移话题”；角色设定禁限继续约束路线。

种子取 `hash(user_id, character_id, source_event_id或occurrence_id, card_version, style_policy_version)`；只在合法集合中确定性选一条。重复请求重放相同路线，下一事件才有新种子，修复不抽新感情方向。允许集合为空时使用明确未知／边界回应，不发明新路线。

最近句式清单来自最后 12 条已提交、可见 assistant 消息，最多取 7 天；记录开场、结束语、常用转折、连续6字片段的归一化指纹与出现次数。它是表达历史缓存，不能成为关系证据。最近连续两条相同开场、或同一固定句7天内出现3次时在本轮 avoid_patterns 中提示；只展示3–5项，缓存可从历史重建。修复候选不进清单。

去掉多处重复的“你只能把对方当挚友”式提示，统一由一张卡片表达当前约束；只在具体 source 支持时提“顾虑”或“心动”。不要通过加入更多固定人格口头禅解决刻板。

### 8.2 采样建议

传感器 temperature=0，严格 schema，固定 model/version；仍记录实际模型输出，因为 temperature=0 不保证 Provider 位级一致。普通表达建议 temperature=0.8，故事0.9，语音0.7，修复0.3，作为离线调参起点。先只调一个随机性参数，top_p 保持 Provider 默认；不同时拉高两者。

presence_penalty / frequency_penalty 默认不设置；只有目标 Provider 和模型明确支持且对照有收益时，才试 frequency_penalty=0.2。不把供应商不支持的参数悄悄丢掉；记录请求参数与实际支持能力。当前 `ai_client` 的 temperature=None 使用 Provider 默认，不代表线上当前温度低。模型不接受温度时靠路线和去重，不谎称调参生效。

### 8.3 验证“中转导致刻板”的假设

本轮不运行。后续获得付费测试授权后，用一份固定、去标识的合成场景，同一模型确切版本，完全相同的 system blocks、messages、schema、卡片、路线种子、max_tokens、采样、thinking 与 cache 设置，中转和官方直连各生成5次，共10次。交错随机顺序，盲化输出，清空最近句式缓存；如模型支持请求 seed，则两边配对同 seed，否则明确随机性无法完全控制。

保存本地请求摘要、请求参数、endpoint类别、返回 model/version、usage、stop_reason、延迟、原始文本和应用后文本，不记录凭证。比对请求是否被截断、system/schema 是否丢失、参数是否被改写、模型是否被替换、响应是否被缓存。对中转返回的 model 名称不能单独信任；缺供应商证据时只报告“返回自称版本”。

每组统计固定句出现率、归一化重复率、句式类别数、直接回答率、盲评自然度。如果原始输出有差异而应用后文本趋同，优先排查本地 sanitizer、Prompt 和降级模板；若中转只有某固定句更常见，不能凭5次认定因果。10次仅为烟雾对照，结果混合则报告不确定；需要扩大到每组至少30次再评估，额外费用另授权。

若直连无法取得同一版本，结果只能比较两个组合服务，不能归因于中转本身。本实验不读取真实聊天、不写状态、不调用后台感情传感器，避免新状态把重复测试的场景改变。

## 9. 评测、指标与通过标准

### 9.1 无模型的时钟快进合成对话

使用虚拟 UTC 时钟、固定 canonical fixture 和预先给定的传感器注解，不等待现实天数、不连接生产、不调用真实 Provider。至少覆盖：

1. gojo 四项100、geto 旧负面标签；相同长期值配不同近期事件，输出不同趋势且无身份断言。
2. 关心→调情→要求空间→修复；分钟、6小时、1天、7天、14天快进，测试平滑、滞后、限幅、空窗口与半衰期。
3. 同消息三次重送、跨渠道重放、乱序到达、不同传输分批、跨 UTC 日和跨用户时区；不重复增量、不绕过额度。
4. 引用、反讽、假设、第三方故事、用户撤回、来源删除和上下文失效；unknown 不改数、失效来源不继续授权。
5. 连续问感情、一次延后、两次实际回避、直接不确定答复、明确拒绝、撤回问题；欠项创建和清偿均一次，感情身份保持独立。
6. 明确提议→双方确认→撤回；目标不匹配与单方表态不确认；用户纠正即时生效。
7. 传感器403、429、timeout、schema错误、批次一条跨用户来源；合法条独立接收，失败不阻塞聊天、不伪造结果。
8. 六入口的假生成：第一段合规、末段越界；JP合规但ZH新增身份；语音流截断、TTS失败与断线恢复，未经整条检查零字幕、零音频。
9. 候选首次违规→修复仍违规→兜底；额度耗尽与来源变化；零重复用户事件、零失败候选副作用、无额外隐形重试。
10. 开关关闭、进程重启、缓存清空、版本回滚和来源重新校验；canonical 账本与用户事实无变化。

### 9.2 固定场景盲评

另建至少24个固定合成场景，覆盖认识初期、熟悉、亲昵但未确认、有有效边界、靠近与回避并存、关系提议、撤回、直接追问、旧账本饱和和缺数据。把“阶段”当评测场景背景，不从数字反推身份。

后续经授权每场景为旧方案和v2各生成3次，共144条；冻结状态、模型版本与参数，随机顺序，至少3名评审独立评价自然度、具体性、角色一致性、正面回答和施压感。评审不见方案名称与分数；允许标记“无法判断”。评测集与阈值调参集分开，不把被看过的场景当独立验收。

| 指标 | 首期通过标准 |

| canonical事实／数值越权、跨用户来源、未经证据确认身份 | 全部确定性fixture为0；盲评中出现任一严重身份／用户事实伪造即停止放量 |

### 10.2 回滚验收

使用读版本指针与停止新候选接收，不删除旧／新审计行。配置回退后重建缓存，只有对应reader允许的版本参与展示；用户事实、旧rel_state、有效declared stance与canonical事件逐项摘要不变。

新欠答案、确认和撤回已经成为真实对话历史，回滚展示策略不能抹除这些事件，也不能恢复后来已撤回的授权。新清偿若依赖失效来源仍须失效；遗留已resolved记录保持历史，不被旧reader误当有效当前结论。重启不跑隐式重算或生产回填。

回滚演练至少覆盖：功能开关中途变化、一个shadow批次进行中、assistant已commit但未交付、来源撤回与缓存未过期、语音Provider中断。验收既检查可用性，也检查没有恢复旧模型判分、旧标签定性或第二权威。

### 10.3 成本估算

本轮模型调用0、生产查询0。以下是规划公式，不是当前供应商报价；上线时必须使用选定模型的实际账单与缓存计费核算。

设传感器每批固定输入开销H=600 tokens，每事件输入u=150、输出v=80，批量b=8，输出固定开销o=80；在消息足够集中、可组成满批时，N条消息用 `B=ceil(N/b)` 次，输入约 `B×H+N×u`，输出约 `B×o+N×v`，再受第3节硬额度限制。分散消息被5分钟定时触发时，批次可能更多、处理覆盖更低，应按实际B核算。超上限的事件留待以后，不假设全部处理。

例：每天40条合格消息、每批8条时，约5次传感器调用，输入9000、输出3600 tokens。若仅为演示假定输入$1／百万、输出$5／百万，约$0.027／角色日、$0.81／30天；每角色每日硬token上限对应约$0.048。用户共享48,000总tokens不能独立推出固定费用，须按各角色输入输出上限及实际组合核算。该单价是算术假设，无已核验报价含义。

闸门检查无模型费；额外修复成本 `F×(I_gen×p_in+O_gen×p_out)/1,000,000`。示例：40轮、5%需要修复，F=2，生成输入6000、输出500 tokens，假定输入$3／百万、输出$15／百万，则额外约$0.051／日；达到5次修复日上限为约$0.1275。这是在原聊天成本之外，不包含长故事、视觉输入、thinking、TTS或缓存差异。
